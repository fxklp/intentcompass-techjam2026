## 6. 接受标准 v2：能力必须完整，允许有限指标回退

下表仍记录 RC3 参考值，不再要求候选逐项零退步。

|---|---:|---:|---:|---:|

| 原 Synthetic Shadow | 200 | .965000 | .703615 | 3.545000 |
| 原 TASK-014 A | 800 | .956250 | .695408 | 3.453750 |
| 原 TASK-014 B | 800 | .956250 | .698810 | 3.515000 |

四组均用相同样本清单和停止规则重新跑 RC3 与候选。每组整体指标相对同组 RC3 的保守工作容忍量：

- HR@10：绝对下降不超过 0.005，即 0.5 个百分点（200 会话最多少命中 1 个；800 会话最多少命中 4 个）。
- MRR：绝对下降不超过 0.005。
- MTTC：平均增加不超过 0.10 轮。

例如 Public 工作边界为 HR >= .975、MRR >= .691861、MTTC <= 3.855；三项分别检查，TechnicalScore 上涨不能抵消单项超限。阈值是上限，不是主动追求的退步额度。若不增加能力的纯优化导致退步，应撤销该优化而不是消耗额度。

场景级不再要求严格零退步，但必须展示四类场景的全部变化、命中数损失和最差退步，不能用总体均值掩盖某场景明显失效。明显集中退步或边界功能失效必须报队长复核；不得只挑好的场景。

能力齐全 + 正确性/范围约束通过 + 三项均在容忍量内：可以申请候选接收，不因轻微掉分自动拒绝。能力未齐全则任务仍未完成，即使分数更高也不合格。超出容忍量时继续做时间允许的修复，并交具体损失和原因请求队长裁决；不擅自扩大阈值、不停用能力冒称完成。

来源可参考 tests/core/check_final_policy.py 的数据复现逻辑、tests/core/check_terminal.py、scripts/shadow_evaluator.py。旧 proof 脚本固定旧源码/结果，不可直接拿来验收新算法；复用数据生成逻辑，新建候选 runner，不修改旧冻结生成器。A/B 已用于历史验证，不能称新 holdout；仅看聚合/场景对比，禁止围绕其目标调参。

先 Public + 小型功能集筛选；每个方向最多两轮有依据的修订，然后整体候选只做有限完整确认，避免把时间耗在无限搜索。声称通过必须保存 results/配置/样本清单哈希/代码 SHA。证据只证明这些测试集，不保证未知最终集永不回归。

速度：无需每次变化都全量 benchmark。最终 RC3/候选用同一主机、交替独立进程测量 3 对，报告初始化、p50/p95/p99、总耗时、峰值内存。RC3 既有 Windows p95 约 102.46ms，仅作参考。建议交互 p95 尽量在 1 秒内；这是团队目标不是官方门槛。超过时优先缓存/批量/有界路由，仍不可接受须报队长，不能改写指标。
